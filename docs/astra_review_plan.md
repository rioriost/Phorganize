## 結論

Core と UI の分離、ネイティブメタデータ API、コピー後に原本を削除する基本方針は維持できる。
全面的な書き直しより、ファイル操作の安全性と実行状態の整合性を優先して修正する。

特に、大小文字を区別しないボリュームへの並列移動で、**2 件成功と表示される一方、
保存先には 1 件しか残らず、原本 2 件が削除される**問題を再現した。
また、コピー後に原本が同じサイズのまま更新された場合、その更新を失う問題も再現した。
アプリ側には、別ウインドウのフォルダー選択によって、表示と違う原本を移動し得る問題がある。
この P1 の 3 件の対処が完了するまでは、重要な原本に移動モードを使用しないことを推奨する。
コピーでも前者により保存先の一方が失われ得るため、成功件数だけを根拠に原本を消去しない。

優先度は P1 = 原本保護のため最優先、P2 = 機能の正確性・運用上の信頼性のため修正、とする。
以下の行番号は対象コミット時点のもの。

## 確認した Core の問題

### C1 / P1: 大小文字を区別しない保存先で並列移動がデータを失う

**箇所:** `Sources/PhorganizeCore/FileOrganizer.swift:73-106, 450-465`

`usedTargets` と重複グループのキーがパス文字列そのものであり、`.jpg` と `.JPG` を
異なる保存先として予約する。一方、通常の大小文字を区別しない APFS では同じファイル名になる。
さらに、存在確認後の `FileManager.moveItem` による確定は、排他的な「既存ファイルを
絶対に置換しない」操作ではない。並列処理が存在確認を通過すると、一方が他方を置換できる。
コピー検証はサイズだけなので、同サイズの別内容なら双方が成功し、移動では両原本を削除する。

**再現:** 同じ撮影日時、同じサイズ、異なる内容の `lower.jpg` と `upper.JPG` を
拡張子保持・並列数 2 で移動。大小文字を区別しない APFS 上の 11 回の試行すべてで、
`moved=2, failed=0, 保存先の実ファイル数=1, 残存原本数=0` となった。
並列数 1 では 1 件成功・1 件失敗となり、失敗した原本は残る。

**修正方針:**

- 保存先ボリュームの名前比較規則を考慮して、同一バッチ内の出力名を予約する。
  大小文字を区別するボリュームで、区別可能な名前を無条件に同一視しない。
- 一時ファイルの確定を、macOS の `renameatx_np(..., RENAME_EXCL)` 等の
  原子的な非置換操作に変更する。事前の存在確認は排他制御の代わりにしない。
- 実行時に別プロセスが保存先を作成した場合も、既存内容を維持して競合を報告する。
  プレビューと異なる名前に暗黙で変更しない。

**完了条件:** 同名・大小文字差・同サイズ別内容の並列コピー／移動、確定直前の競合、
大小文字を区別する／しない保存先で、上書きも誤った原本削除も発生しない。
同じ plan 内だけでなく、複数ウインドウから同じ保存先に実行される別 plan 間の競合も対象とする。
成功した移動 1 件につき対応する正しい保存内容が存在する。

### C2 / P1: コピー後の同サイズの原本更新を検出せず削除する

**箇所:** `Sources/PhorganizeCore/FileOrganizer.swift:206-209, 408-418, 574-610`

原本の同一性は device/inode だけで判定し、内容の検証はサイズ比較だけである。
別アプリが同じファイルを上書き編集しても inode とサイズが変わらなければ、
コピーに含まれていない更新を削除してしまう。
既存保存先の重複判定に使っている SHA-256 は、新規コピーの検証には使われていない。

**再現:** 注入した `FileManager` でコピー確定直後に原本を `ORIG` から `EDIT` へ
同じ inode のまま書き換えた。結果は移動成功・失敗 0 件、保存先は `ORIG`、
原本は削除され、`EDIT` は残らなかった。

**修正方針:**

- 原本の identity、サイズ、mtime/ctime 等をコピー前後と削除直前で照合する。
- 少なくとも移動モードでは、安定した原本の読み取りとコピー内容の SHA-256 検証を行う。
  コピー完了後に変化を検出した場合、保存済みコピーと原本を残し、部分成功として報告する。
- パスの再解決だけに頼らず、読み取り対象のファイル記述子と identity の対応を保つ。
- 任意の外部ライターとの競合を stat/hash の追加だけで完全に解消したとはみなさない。
  保証範囲を「処理中に更新されない原本」に明記し、検出可能な変更では安全側に停止する。

**完了条件:** 同サイズの上書き、サイズ変更、原本差し替え、検証失敗、削除失敗で、
保存していない内容を削除しない。通常のコピー／clone／移動の成功動作は維持する。

### C3 / P2: 読めないサブフォルダーを無通知で除外する

**箇所:** `Sources/PhorganizeCore/FileOrganizer.swift:355-395`

再帰列挙にエラーハンドラーがなく、列挙器を作れない場合は空配列、
属性取得エラーは `try?` とフィルターで除外される。
「ファイルがない」と「読み取れなかった」を区別できず、取り込み漏れが成功扱いになる。

**再現:** JPEG を置いたサブフォルダーの権限を `000` にして再帰計画を実行すると、
例外なし、計画 0 件、メタデータ／未対応スキップも 0 件となった。

**修正方針:** 列挙エラーと属性取得エラーをパス付きで収集するか、計画を失敗させる。
一部だけ続行する場合は `OrganizationPlan` / `OrganizationSummary` と UI に不完全な
列挙結果を明示し、「すべて取り込めた」と解釈できる完了表示を避ける。

**完了条件:** 権限不足、取り外し、途中で消えたフォルダーを、空の正常な入力と区別できる。

### C4 / P2: バッチの構成が変わると既存の同一ファイルを再コピーする

**箇所:** `Sources/PhorganizeCore/FileOrganizer.swift:73-106`

同日時の候補が複数なら `_1` から、単独なら接尾辞なしから検索し、
最初の未使用名を見つけた時点で探索を終える。別の接尾辞に存在する同一内容を確認しない。

**再現:**

- A/B を一緒に取り込んで `_1` / `_2` が存在する状態で B だけを再取り込みすると、
  接尾辞なしの新規コピーを計画し、同一ファイルのスキップは 0 件。
- A だけを取り込んだ後に A/B を取り込むと、A も `_1` として再コピーする。

**修正方針:** 重複探索と空き名前の割り当てを分離する。
対応する日時・フォルダー・拡張子の名前候補群について、既存の接尾辞なし／連番付き
ファイルのサイズ・ハッシュを調べてから空き名を割り当てる。
全アーカイブのハッシュ索引は必須ではない。C1 の名前比較規則と共通化する。

**完了条件:** バッチの追加・部分再実行・並び替え・連番の欠番があっても、
同じ候補群に既に保存された同一内容を再コピーしない。

### C5 / P2: EXIF の撮影日時候補と UTC オフセットの組み合わせが不正

**箇所:** `Sources/PhorganizeCore/MediaMetadataExtractor.swift:52-60`

日時を Original → Digitized → TIFF の順に選ぶ一方、オフセットは常に
`OffsetTimeOriginal` を使う。Digitized のみを持つ画像では、その画像が記録した
`OffsetTimeDigitized` が無視され、保存日が変わる場合がある。

**再現:** `DateTimeDigitized=2025:02:06 01:00:00`、
`OffsetTimeDigitized=+09:00`、出力タイムゾーン UTC の JPEG が、
正しい `2025-02-05T16:00:00Z` ではなく `2025-02-06T01:00:00Z` と解釈された。

**修正方針:** Original/OffsetTimeOriginal、Digitized/OffsetTimeDigitized、
TIFF DateTime/OffsetTime を対応付ける。候補が無効なら次の候補を試し、
最後にファイル属性日時へフォールバックする。

**完了条件:** 各タグの組み合わせ、異なるオフセットの併存、日付境界、
不正な第一候補を含む画像で、正しい絶対日時と保存日になる。

### C6 / P2: 日時のフォールバックで取得済みのカメラ／レンズ情報を捨てる

**箇所:** `Sources/PhorganizeCore/MediaMetadataExtractor.swift:44-65, 114-128`

画像の日時がないと、取得済みのカメラ／レンズ情報を含む結果自体を返さず、
後段のファイル属性フォールバックが両フィールドを `nil` にする。
動画も日時が見つからない場合は同様。日時だけが欠けたメディアが `(null)` 配下になる。

**再現:** カメラ `Review Camera`、レンズ `Review Lens` を持ち、EXIF 日時を持たない
JPEG から、カメラ／レンズがどちらも `nil` として返された。

**修正方針:** フィールド単位で取得結果を保持し、日時だけをファイル属性で補完する。
日時の由来と、カメラ／レンズ情報の有無を混同しない。

**完了条件:** 日時だけ欠損した画像／動画でカメラ／レンズフォルダーが維持され、
全メタデータ欠損時の `(null)` フォルダーも従来どおり機能する。

### C7 / P2: 明示したタイムゾーンオフセットを初期化時に無視する

**箇所:** `Sources/PhorganizeCore/Models.swift:49-60, 99-103`

`OrganizationOptions(timezoneOffsetHours: 9)` と指定しても、
`timezoneIdentifier` に現在地の識別子が入り、`timeZone` はそちらを優先する。
旧設定のデコードではオフセットが採用されるため、初期化方法によって結果が異なる。

**再現:** `TZ=UTC` では、オフセット 9 を指定する既存の
`testDateCameraAndDuplicateTargetNames` と `testMissingCameraUsesNullDirectory`
が、09:16:16 と 18:16:16 の不一致で失敗する。東京環境では問題が隠れる。

**修正方針:** 識別子と旧オフセットの優先順位を一本化し、明示指定と未指定を区別する。
識別子が明示されれば優先し、オフセットだけが指定されれば固定オフセット、
どちらも未指定なら現在のタイムゾーンを使う。旧設定デコードとの互換性を維持する。

**完了条件:** UTC、東京、夏時間のある地域、半時間／45 分の地域で、
初期化・設定の保存復元・出力日時が一貫する。

## 確認したアプリ・配布構成の問題

### A1 / P1: 別ウインドウの選択によって表示と違う原本を移動し得る

**箇所:** `Sources/PhorganizeApp/PhorganizeApp.swift:366-377`
関連: `11-12, 130-131, 332-347, 398`

`WindowGroup` 内の各ウインドウは独立した `AppModel` と表示パスを持つ一方、
`resolvedURL()` は共通の `UserDefaults` から実行時点の bookmark を取得する。
ウインドウ 1 で元 A／先 X を選んだ後、ウインドウ 2 で元 B／先 Y を選ぶと、
ウインドウ 1 の表示は A／X のままでも、実際の処理対象は B／Y となる。
移動モードなら、ウインドウ 1 で確認したものとは違う原本を削除する。

bookmark 作成失敗時に以前の bookmark を残す経路もあるため、
単一ウインドウでも表示パスと実際に解決される URL が食い違い得る。

**根拠:** GPT-6 Astra による静的な呼び出し追跡に加え、実際の `AppModel` を使う
限定プローブで不一致を確認した。設定ストアだけを共有・メモリ内の `UserDefaults`
サブクラスに差し替え、organizer を無処理 stub とし、検査用 accessor から
実際の security-scoped bookmark の生成・解決を呼び出した。
モデル 1 の元／先の表示パスが変わらないまま、モデル 2 の選択後にはモデル 1 の
`resolvedURL()` がモデル 2 の元／先を返すことを確認した。
`run()` はこの解決結果を source/destination に使い、モデル 1 の options と組み合わせる。
GUI の複数ウインドウ操作、`run()`、実ファイルのコピー／移動は実行していない。
bookmark 生成失敗の経路は静的確認のみ。

**修正方針:**

- ウインドウごとの選択を許すなら、そのモデルが選択 URL と bookmark を一緒に所有する。
  全ウインドウで選択を共有するなら、表示も含めて単一の状態モデルを共有する。
- 実行開始時に表示と対応する source/destination/options をスナップショット化し、
  以降は共有設定から対象を読み直さない。
- bookmark 保存失敗は通知し、以前の bookmark を新しい表示パスと組み合わせない。
- 設定ストアと bookmark 解決を注入可能にして、UI を起動せず状態の整合性を確認できるようにする。

**完了条件:** 同一設定ストアを使う 2 モデルで、他方の変更により表示と実行対象が
食い違わない。bookmark 作成・復元失敗、処理開始前後の設定変更でも同様。

### A2 / P2: ファイル日時 API の privacy manifest の申告理由が用途と合わない

**箇所:** `Sources/PhorganizeApp/PrivacyInfo.xcprivacy:16-20`

現在の `C617.1` はアプリコンテナ等にあるファイル向けの理由だが、
主要用途はユーザーが選択したカメラ媒体・外付けディスク等の日時取得である。
この用途に対応する `3B52.1` を実際のアクセス範囲に合わせて申告する必要がある。
現在の宣言が Release の `.app` にも同梱されることを確認している。
実行時のアクセス許可の問題ではなく、配布時の申告整合性の問題であり、
審査で実際に拒否されたという指摘ではない。

**根拠:** [Apple の Required Reason API 理由定義](https://developer.apple.com/documentation/bundleresources/app-privacy-configuration/nsprivacyaccessedapitypes/nsprivacyaccessedapitypereasons)
と実装のアクセス範囲の照合。

**修正方針:** ファイル日時 API の呼び出し箇所と理由を対応付け、
該当する理由に更新する。複数の用途がある場合は、それぞれの正当な理由のみを宣言する。

**完了条件:** ソースの manifest と配布 archive の manifest が一致し、
ユーザー選択ファイルへの実際のアクセスを説明している。

### A3 / P2: coverage gate の成果物パスが Apple Silicon 固定

**箇所:** `scripts/check_coverage.sh:5-6`

成果物の場所を `arm64-apple-macosx` に固定しているため、Intel Mac では
テストが通っても `llvm-cov` が正しい実行ファイルを見つけられない。
README と Package.swift は現在のアプリを Apple Silicon 限定とはしていない。
これはパス構築の静的確認であり、Intel 実機での実行確認は行っていない。

**修正方針:** `swift build --show-bin-path` 等で現在の構成の成果物ディレクトリを取得する。
coverage データ側も同じビルド構成から解決する。

**完了条件:** arm64／x86_64 で成果物を発見し、レポート生成と指定閾値の判定が機能する。

## 修正順序

| 順序 | 作業単位 | 対象 | 依存関係・完了判断 |
|---|---|---|---|
| 1 | 保存先競合と非置換確定 | C1 | 最優先。並列移動で原本消失を起こさないことを先に固定する |
| 2 | 表示と実行対象を同じ状態に統一 | A1 | 意図しない原本への操作を防ぐ。1 と独立して着手可能 |
| 3 | 移動の原本変更検出と内容検証 | C2 | 1 の安全な確定処理に接続し、失敗時は原本を維持する |
| 4 | 列挙エラーの表現と通知 | C3 | Core と UI を同時に変更し、不完全な取り込みを区別する |
| 5 | 既存重複探索と名前割り当ての分離 | C4 | 1 の名前比較規則を再利用する |
| 6 | 日時・部分メタデータ・設定互換性 | C5 / C6 / C7 | 入力メタデータから保存パスまで一貫して確認する |
| 7 | 配布申告と coverage の環境依存修正 | A2 / A3 | 配布成果物と対応アーキテクチャの契約に合わせる |

各作業単位は再現ケースを回帰テストとして固定してから修正する。
既存の「同一ファイルは移動モードでもスキップする」仕様は、この修正で暗黙に変更しない。

## 設計上の補足と範囲

- 計画時の「名前が空いている」は実行時の保証にならない。
  名前の予約と、実際に上書きせず確定できたという事実を分けて扱う。
- 移動の成功条件を「サイズが同じ」ではなく、
  「対応する内容が保存され、検出可能な原本変更がなく、その原本だけを削除した」と定義する。
- `TargetPlanner` が `FileManager.default` に直接依存する一方、実行処理には
  `FileManager` を注入できる。名前比較・既存ファイル照会・確定操作の境界を整理し、
  競合や I/O 失敗を決定的に再現できるようにする。大規模な抽象化は不要。
- 電源断時の耐久性、古い macOS 上での実機動作、すべての RAW／動画形式の実ファイルは
  今回保証していない。通常のコピー検証と電源断耐性を同一視せず、必要なら
  同期書き込み・中断後の一時ファイル回収を別途設計する。
- sandbox 版を終了・再起動した後の bookmark 復元と security scope の開始順序は、
  追加の実機確認対象とする。現時点で再起動時に必ず失敗するとは判断していない。
  stale bookmark の更新、終了／キャンセル時の方針も明文化する。
- SwiftUI の状態・永続化を対象とする試験経路を追加する。
  Core の行カバレッジだけでは、A1 の表示と実行対象の不一致は捕捉できない。
- 修正時には `docs/implementation_plan.md` の古い「将来の sandbox 対応」等の記述を
  実装に合わせて更新し、README に移動の保証範囲と部分失敗の扱いを明記する。
